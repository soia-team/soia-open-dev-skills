# 任务书模板与写作准则

派发外部 AI CLI 前，把请求写成一页**任务书**。任务书是执行者的权威规格：原对话、工单正文和历史讨论是背景，任务书本身才是契约。本文件给出 7 字段模板、四条写作原则、三段式交付契约、证据有效性优先的 check 0，以及收敛上限。

主文件按需一跳加载本文件；认领字段与抓取判据见 `claim-protocol.md`，禁止句改写见 `writing-positive-constraints.md`。

## 四条写作原则

任务书可能在队列里停留数天，期间代码会被重命名、移动和重构。四条原则共同保证它到期仍可用。

1. **以耐久换精确（Durability over precision）。** 描述接口、类型和行为契约，点名执行者应当寻找或修改的具体类型名、函数签名或配置形状。定位信息落在接口与行为上，这样文件改名、行号漂移后任务书依然指向同一个目标：读的人沿类型名就能找到当下的实现。
2. **写行为，不写步骤（Behavioral not procedural）。** 说明系统应当表现出什么，把实现路径留给执行者现场勘查后自行决定。正面例：「`SkillConfig` 类型接受一个可选的 `schedule` 字段，类型为 `CronExpression`」；反面例：「打开 `src/types/skill.ts`，在第 42 行加一个 schedule 字段」。写行为的写法让执行者按当下代码结构落地，而不是按写任务书那一刻的目录快照落地。
3. **验收标准逐条独立可验证。** 执行者需要知道什么时候算完成。每条验收标准都要能被单独证伪：正面例「运行 `gh issue list --label needs-triage` 返回已做过初始分类的条目」；反面例「分类功能工作正常」。逐条独立的写法让主控能一条一条对证据判定，而不是对一份整体印象判分。
4. **显式范围边界。** 写明范围之外有什么。这条让执行者把改动收在目标内，不必猜相邻特性算不算本次任务；范围边界同时是主控核对 diff 的比对基线。

> 正负写法对照与「禁令必须配正向目标」的规则见 `writing-positive-constraints.md`。

## 7 字段模板

```markdown
## 任务书

**类别（Category）：** bug / enhancement
**摘要（Summary）：** 一句话说明要发生什么

**当前行为（Current behavior）：**
描述现在发生什么。缺陷任务写坏掉的行为；增强任务写新特性所基于的现状。

**期望行为（Desired behavior）：**
描述执行者完成后的行为，并写清边界情形与错误条件。

**关键接口（Key interfaces）：**
- `TypeName`：要改什么、为什么
- `functionName()` 返回类型：现在返回什么、应当返回什么
- 配置形状：需要新增的配置项

**验收标准（Acceptance criteria）：**
- [ ] 具体、可测的标准 1
- [ ] 具体、可测的标准 2
- [ ] 具体、可测的标准 3

**范围之外（Out of scope）：**
- 本任务不涉及的相邻特性或文件
```

派发时在任务书头部补两个字段：`claimed_by`（认领者，留空即可被抓取）与 `gate_tier: A|B|C`（复审强度档）。两者的判据见 `claim-protocol.md`。

## 完整反例（逐条剖析）

下面这则任务书架不住，走一遍四条原则就能看出每一处缺口。**它的问题不在写得短，而在每条信息都指向会失效或无法验证的东西。**

```markdown
## 任务书

**摘要：** 修一下派发那个 bug

**要做的事：**
派发那块坏了。看主文件修一下，问题在那个大概第 150 行的函数附近。
顺手把相关的都理顺，该加的测试加上。

**要改的文件：**
- src/dispatch/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

逐条剖析：

| 缺口 | 触发违反的原则 | 后果 | 改法 |
|---|---|---|---|
| 无类别、无当前/期望行为 | 写行为 | 执行者不知道是修缺陷还是加能力，只能挑一种猜 | 补类别，并写清现状与目标行为 |
| 引用文件路径与行号 | 以耐久换精确 | 队列里躺两天后路径与行号双双失效，执行者按错位的行号改到无关代码 | 改为点名类型、函数签名与配置形状 |
| 无验收标准 | 逐条独立可验证 | 执行者自报完成，主控无逐条可判的证据 | 补 3–5 条可单独失败的验收标准 |
| 「顺手理顺相关的」 | 显式范围边界 | 改动无上界，diff 卷进无关重构 | 把「相关」写成具名范围，其余进范围之外 |
| 「该加的测试加上」 | 写行为 + 验收标准 | 测试范围与形式全凭执行者发挥，覆盖不到真正的行为 | 在验收标准里写清哪条行为由哪个检查证明 |

## 三段式契约：Input / Workflow / Output + Verdict

任务书交付的产物按三段式收口，执行者按同样的三段回执。三段各有自己的完成判据：

| 段 | 内容 | 判据 |
|---|---|---|
| Input Contract | 本次任务接受的输入：基线、允许范围、真源链接、必需证据 | 必需输入缺失时在回执首行点名，并就可评审部分继续 |
| Workflow | 执行者实际走的检查与动作次序 | 每步写出实际命令或动作，不写打算做什么 |
| Output Contract | 回执的固定节区与字段 | 节区齐全；缺项写明缺什么，不用散文补位 |
| Verdict | 一行裁决词 + 支撑它的证据引用 | 词由证据导出，不由感受导出 |

三段式让回执可被机械核对：Input 段说明边界，Workflow 段提供可复跑动作，Output 段保证字段可比对，Verdict 段给出结论与它的出处。

## 回执硬要求：执行面板收敛

执行者是本次任务面板与计划项的所有者。结束前把自己创建的条目**全部置为完成**，回报固定含一行自检声明：

```text
执行面板已全部收敛
```

确有未完成项时，逐项写出未完成原因、当前状态与下一步归属。面板里留着进行中项而回报只写「交付完成」，属执行者收尾纪律缺口而不是交付缺口——上级在面板上看到的「N 进行中」会把已完整交付的任务读成未结束。

主控收单时核对面板完成度与这行声明是否一致（验收动作见 `dispatch-contract.md` 的反虚假修复门禁）；不一致按回报缺陷退回，不进入验收结论。

## check 0：证据有效性优先

**证据检查先于一切其他检查。** 在任何内容判断之前，先确认该有的证据都在、且每条证据有效：

- **齐备**：任务书点名的必需证据全部存在。约定的视口、状态、入口、产物一项不缺。
- **有效**：证据与它自称的内容一致——文件名声称是结算页，图里就必须是结算页；该看到页面顶部的整页截图，顶部就得在；尺寸要与它声称的视口相符。
- **非空**：没有整块空白、黑屏或明显截断。

**缺失与损坏同等处理：没人采集过的视口，就是没人检查过的视口。** 任一必需证据不合规时，整次评审换形态：回执首行给 `disposition: recapture`，只写一节列出每个缺失或失真的证据、以及它的合规版本应当呈现什么，然后停止。

在损坏证据上继续建判断矩阵，等于把损坏洗成通过——上级拿到的是一个建立在坏输入上的结论，还得在有效证据上重做一次完整评审。因此正确的动作是**先把它挡回采集环节**，而不是降级评分。

## 裁决词表与收敛上限

回执首行是四个词之一：

```text
disposition: recapture | rebuild | fix | ship
```

这四个词就是全部词表，不另造第五个。词由证据导出：

| 词 | 触发条件 |
|---|---|
| `recapture` | check 0 未通过：证据缺失或失真 |
| `rebuild` | 焦点产物的根本方向已被否定，需要按真源区域重新推导 |
| `fix` | 修复清单非空 |
| `ship` | 判断矩阵中不存在被否定或缺席的行 |

配套三条硬上限，用来把评审收敛到可控轮次：

- **修复清单最多 8 条**，按实质程度排序，行为性失败排在工艺性问题之前，每条一行并挂到具体的检查或契约承诺上。
- **约第 10 轮停止阅读、开始写。** 阅读是配额而不是许可：按批读入，先取必需证据、任务书与契约，对产物抽样主文件而不遍历目录树，到约第十轮就动笔；未读的部分在节区上方一行点名。
- **裁决词原样上报。** 上级照抄执行者给的裁决词，不改写、不软化。
