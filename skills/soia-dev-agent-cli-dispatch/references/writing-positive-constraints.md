# 正向约束写法（positive constraints）

技能正文与任务书里的约束有两种写法：**正向目标**（「只改 X」）和**禁令**（「不要碰 Y」）。本文件给出改写准则与三组来自本仓现有技能正文的改写实例，用于把禁止句系统性地改成正向表述。

## 规则

1. **正向表述目标。** 写清要做的事，读者据此可以直接执行。「只改 X」给出范围与动作；「不要碰 Y」需要读者先枚举 Y，再自行推出边界。正向写法省掉这次推导，也省掉它可能推错的空间。
2. **禁令只作硬护栏。** 禁令保留给不可逆、涉及安全或授权的边界：删除、覆盖、发布、远端写入、凭据、权限变更。这些地方需要一条明确不能越过的线，正向描述不足以承载它。
3. **硬护栏必须配正向目标。** 每条禁令旁边写出对应的正面动作。只写「不得删除未提交内容」，读者知道不能做什么却不知道要做什么；配上「删除前先确认归档 commit 已落盘（`git log` 验证），确认后再删」才是一条可执行约束。
4. **正向写法改善上下文效率。** 禁令要求读者在脑内构造一个被禁止的行为再抑制它；正向目标直接给出目标状态。同一个约束用正向写通常更短，且不容易在长上下文里被读成一句可以跳过的警告。

**一条合用的硬护栏长这样：** 正面动作在前，禁令在后作为它的边界。

```text
提交前只 `git add` 本任务文件清单里的路径；`git add -A` / `git add .` 会把工作树里的无关改动一并卷入，因此在本仓禁止使用。
```

## 三组改写实例

### 组 1：范围边界

技能正文原文（`soia-dev-enforce-coding-protocol`，短协议「按风险加验证」）：

```text
只在授权范围内排查同类模式，不顺手扩大清理。
```

改写后：

```text
只在授权范围内排查同类模式；范围外的同类问题登记为单独事项，交给主控决定是否另开任务。
```

改写理由：「不顺手扩大清理」禁止了一个模糊动作，读者仍需自行判断什么算「顺手」。改写后给出两个动作——范围内排查、范围外登记——边界由「授权范围」这一既有事实决定，不再依赖程度判断。禁令退为「只在授权范围内」这条线的补语。

### 组 2：验证诚实

技能正文原文（`soia-dev-implement-task`，交付与边界）：

```text
不吞错、不削弱断言或静默降级来变绿；保留历史失败，区分本次通过与未覆盖的全局问题。
```

改写后：

```text
让检查结果如实反映行为：修复根因并使检查转绿；无法在本次范围内修复时保留失败原样，在回执里写明缺口与它的影响。历史失败与未覆盖的全局问题分开列出。
```

改写理由：原句列举了四种伪修复手法，读者要先把四种手法在脑内过一遍才能确认自己没踩。改写后先给目标动作「修复根因并使检查转绿」，再给退路「保留失败并写明缺口」——两条都是可执行的。原禁令所保护的「如实反映行为」升为首句的正向目标，不再需要靠否定式兜底。

### 组 3：交付声明

技能正文原文（`soia-dev-design-ui`，设计方法）：

```text
内容和品牌资产缺失时明确占位与影响；不猜品牌色、不把假数据或静态交互包装为已接通能力。
```

改写后：

```text
内容和品牌资产缺失时，用占位内容并写明它对交付的影响。把每项能力的真实状态写进交接说明：已接通的写已接通，假数据与静态交互标为占位，品牌色取自已批准的设计真源。
```

改写理由：原句的三条禁令各自指向一个具体失真形态，改写后归到一条正向要求上——「把每项能力的真实状态写进交接说明」，并给出三个分类的落点。声明规则一旦正向化，新增的能力类型（新占位形态、新真源）自动落进同一条规则，不必逐项补禁令。

## 改写检查

对每条约束问四句：

1. **它给出动作了吗？** 读者能否不回推就执行。
2. **它是硬护栏吗？** 涉及不可逆、安全或授权才保留禁令形态。
3. **护栏旁边有正向目标吗？** 没有就补上。
4. **改成正向表述后是否更短？** 更短说明原文的禁令部分在承担措辞而非约束。
