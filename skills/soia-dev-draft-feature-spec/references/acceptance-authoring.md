# 验收标准起草

本文件是 `soia-dev-draft-feature-spec` 的验收标准写作参考：**每项必需能力对应一条可判定的验收标准**。SKILL.md「写清功能」的第三条按本文件展开。

裁决侧见 `soia-dev-implement-task` 的 `references/acceptance-line.md`；本文件管起草，即把标准写成下游能逐条判定的形状。

## 起步：先定完成契约

起草验收标准之前先声明本次规格按哪种完成态交付：

| 契约 | 成立条件 | 交付内容 |
|---|---|---|
| **Closed** | 每项必需能力都有可观察验收，开放项已逐条登记去向 | 完整规格 |
| **Open** | 仍有会改变范围或验收的未知 | 最强有界规格 + 待决事项 + 每项的 owner 或归属缺口 + 下一触发条件 |

起草切片不代表已经建立或授权 Goal/Task；规格本身以这两种形态之一交出去。

## Clarity × Demand：两条性质

验收标准的强弱由两条性质共同决定，两条都要过：

- **Clarity（可判定）**：读者能否分清「完成」与「未完成」。含糊的界（「体验良好」「基本可用」「已处理」）会招致**过早收口**，注意力滑向「看起来做完了」。收紧界是第一顺位、成本最低的动作。
- **Demand（负载）**：它要求多少工作量。「每一个受影响的入口都已覆盖」比「列出入口」强制出更多调研。`Demand` 不绑定条目数：一条「全部规则已应用」同样给一份平铺清单加上穷尽性门槛。

**最强的标准同时是可判定的与穷尽的。** 判据写完后逐条问两句：这条能不能判出完成与未完成？这条能不能让偷懒的通过方式落空？

## 每条标准的形状

```text
前置条件 → 动作 → 可观察结果（+ 关键失败 / 边界）
```

| 差 | 好 |
|---|---|
| 「分类功能工作正常」 | 「运行 `gh issue list --label needs-triage` 返回已做过初始分类的条目」 |
| 「错误处理完善」 | 「网络超时时显示可重试的错误态，重试后回到加载态」 |
| 「性能可接受」 | 「列表首屏在目标视口下 LCP < 2.5s（第 75 百分位）」 |
| 「支持导出」 | 「导出 CSV 时，空结果导出的文件含表头且零数据行」 |

写法要点：

1. **一条一项。** 把并列的能力拆成多条，让下游能一条一条判定；一条里塞三件事时，通过一半无法表达。
2. **每条独立可验证。** 一条失败不影响其余各条的判定，裁决表才有分辨力。
3. **结果可观察。** 写用户或消费者能观察到的东西，不写内部实现状态。
4. **覆盖关键失败与边界。** 异常、重试、取消和数据变化按真实相关路径各给一条。
5. **不提前锁死技术实现。** 标准描述行为，实现路径留给设计阶段。

## 负控：起草时就写反例

**每条标准都要有一条能失败的路径。** 写不出「什么情况下这条会失败」的标准还不是验收标准，只是愿望。

起草时给每条标准配一句反例或负控说明：

```text
A2  网络超时时显示可重试的错误态，重试后回到加载态。
    反例：超时后停留在加载态不报错 → 本条失败。
```

四种可用的负控形态，任选其一并记下：观察修复前失败、临时改坏被测行为、植入范围受控的违规、使用已知违规的输入。下游会用同一条要求复核实现侧新增的检查——**新检查必须被证明有能力失败**；起草时就写明反例，让这道证明有据可依。

## 规格的 Closed / Open

沿用同一套完成契约：

- **Closed**：每项必需能力都有可观察验收，反例写明，开放项已逐条登记去向，没有已知未知还能改变范围或验收。此时规格可交下游实现。
- **Open**：存在会改变范围、权限或验收的未知。此时交付四段——最强有界规格、会改变决策的未知、该未知的 owner 或归属缺口、下一份证据或决策触发条件。

规格起草完之后，逐项复核必需范围没有遗漏、矛盾已暴露、预期可验证。

## 交付前自检

1. 每项必需能力都有对应验收标准，没有只写在正文里的能力。
2. 每条标准同时通过 Clarity 与 Demand 两问。
3. 每条标准配了反例或负控说明。
4. 并列能力已拆成独立条目。
5. 开放项逐条有 owner 与下一触发条件。
6. 完成态已声明（Closed 或 Open）。

## 来源与承接说明

- **Clarity × Demand 双性质**：承接自 `mattpocock` 仓 `productivity/writing-for-agents/SKILL.md` 的 completion criterion 两性质（外部概念：Clarity 决定能否分清完成与未完成，含糊的界招致过早收口、可见的后继步骤提供拉力而判据的清晰度提供阻力；Demand 决定调研负载；最强的判据同时是可判定的与穷尽的）。
- **验收标准的可测对照与复选清单形态**：承接自 `mattpocock` 仓 `to-spec` 的 Testing Decisions 段与 `to-tickets` 的 Acceptance criteria 复选清单（外部概念）；本仓补入「反例/负控说明」一列。
- **负控要求（新检查必须能失败）**：承接自 `lencx` 仓 `coding-protocol/references/verification.md` 的 Prove Sensitivity 一节（外部概念，四种负控手法原样承接）；本仓把它从「实现侧检查」前移到「起草侧标准」，让标准在写下时就带着可失败路径。
- **Closed / Open 双完成契约**：承接自 `lencx` 仓 `keel/SKILL.md` 的完成态定义（外部概念）；本仓用在规格侧——规格的完成态决定它是可交下游实现（Closed）还是四段结构化开环交付（Open）。
- **本仓首创**：「逐条 acceptance criterion 对照证据判定」三步裁决步由本仓自建，落在 `soia-dev-implement-task/references/acceptance-line.md`；本文件的第 1 条交付自检（每条标准都能被那三态判定承接）即为其起草侧对应要求。三仓与本仓此前共同缺失这一步，不可承接。
- **实战素材（指令号）**：`owner-directives` 指令 219③（每单验收时未解决问题逐条定去向后才销账）为「开放项逐条有 owner 与下一触发条件」的一手来源；指令 222（v61 大对账凭表述补 passed 的事故，纠正为「图状态回写必须逐条附一手证据」）为「标准必须写成可逐条判定、且每条挂得上证据」的一手来源；指令 193（15 个越界状态词改合法词，负向测试确认能红）为负控要求的一手来源。
