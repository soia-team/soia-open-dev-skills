# 失效模式索引：编码协议

本文件是 `soia-dev-enforce-coding-protocol` 短协议的维护索引，记录每条条款在挡什么。它不是「一条规则配一个测试」的要求：合并重叠的行，删掉不再改变协议的条目。

用法：起草或复审任务书时，按本表核对本次改动可能落入的失效模式；表末的实战素材行来自真实事故，是条款的主要来源。

## 失效模式 → 机制 → 条款

| 失效模式 | 机制（为什么反复发生） | 对应条款 |
|---|---|---|
| **假 passed**：把「上游报告说完成了」当作完成证据写进状态真源 | 对账时逐条回到一手证据比采信表述贵得多，而采信在当下没有任何报错 | 验证行为本体 |
| **机械门全绿下的内容错误**：格式与链接检查全过，结论本身是错的 | 机械门只能管住可机械判定的性质；「内容是否正确」不在它的判定域内，绿了容易被读成「都没问题」 | 验证行为本体；到证据足够就停 |
| **未验证的删除**：归档命令报错空转未被察觉，随后照计划删树 | 删除段的执行与归档段的成功判定是两件事，脚本退出码不为零时流程仍会往下走 | 先找证伪办法 |
| **glob 空转**：通配符无匹配时静默成功，被当作「已归档」 | 无匹配在多数 shell 语义下不是错误，空结果与成功结果同形 | 先找证伪办法 |
| **`git add -A` 卷入无关改动**：脏工作树上提交把他人未提交文件一并带走 | 一条命令比逐路径列举省事，而代价只在 diff 里才可见 | 守住请求 |
| **污染基线**：基于挂着未推 commit 的分支开工，产出卷入无关变更 | 建分支前核对基线与远端对齐是一步额外动作，跳过它当时没有任何反馈 | 守住请求；先找证伪办法 |
| **哨兵自匹配**：监控把自己的输出匹配成「有活动」，实际进程已死 | 判活信号与产出信号共用同一个日志面，自匹配在文本层面无法区分 | 先找证伪办法 |
| **自报身份失真**：执行器回执自称的模型与实跑不符 | 执行器的自报来自缓存或默认值，缓存损坏时它仍然给出一个看起来正常的名字 | 验证行为本体 |
| **叙述代替证据**：执行器以「正在运行」结束会话而进程已死 | 过程叙述与产物落盘是两条证据链，前者更容易生成 | 验证行为本体 |
| **子进程随会话退出被杀**：长任务由短会话拉起，会话结束即中断 | 归属关系决定了生命周期，而启动那一刻看不出这层依赖 | 按风险加验证 |
| **空输入照跑**：写 prompt 前的目录创建失败，执行器收到空输入正常启动 | 重定向失败与写入成功在调用方看来都是「命令返回了」 | 先找证伪办法 |
| **状态词越界**：自评时造出词表以外的状态值 | 现有词表表达不了想说的意思时，造一个新词比回到定义更省事 | 守住请求 |
| **未解决问题蒸发**：未闭合项没有指定去向就随任务销账 | 销账的判据是「任务结束」，而悬项的判据是「有去向」，两者不在同一处检查 | 到证据足够就停 |
| **修复漂移**：顺手修掉与当前任务无关的缺陷 | 改动就在手边，单独登记为事项比直接改贵 | 守住请求 |
| **静默降级**：吞错、TODO、放松断言或删掉失败测试来变绿 | 让检查通过比修复根因便宜，而绿色在多数流程里就是通行证 | 验证行为本体 |
| **空转测试**：新检查没有负控，不跑被测行为也会通过 | 一个从未失败过的检查与一个有效的检查在输出上同形 | 先找证伪办法 |
| **缺陷固化测试**：断言当前输出而不是要求的行为，把缺陷锁成事实 | 照现状写断言比回到需求写断言省一次推导 | 先找证伪办法 |
| **无关验证**：拿一个通过但不覆盖本次改动的检查充当正确性证明 | 「有检查通过」与「该项行为被检查过」在回执里都表现为一行绿 | 按风险加验证 |
| **验证膨胀**：改动很小却重跑全套检查或改动环境 | 全套检查不需要判断覆盖面，聚焦检查需要先想清楚改动的爆炸半径 | 按风险加验证；到证据足够就停 |
| **反复试错**：连续失败的修复尝试不断扩大爆炸半径或来回翻转方向 | 每次尝试都让对方看起来更接近答案，而停下来诊断需要先承认前几次无效 | 到证据足够就停 |
| **需求静默丢失**：回执报完成，请求的一部分被重新解释或略过 | 混合任务里各部分的适用条款不同，逐条回执比整体汇报贵 | 守住请求；验证行为本体 |
| **技能送达≠技能生效**：技能清单已送到执行端，执行者一个技能正文都没加载 | 任务书把步骤写全后，加载技能看起来是多余动作；触发词面向人类口语，与任务书书面语匹配度低——2026-09-12 实测两者在真实任务书上零重叠，靠触发词命中不可依赖 | 任务书「适用技能」字段 + 回报第一节加载清单（见下方两个一手数据节） |

## 一手数据：技能送达≠技能生效（2026-09-11）

**判据：在同一份执行端会话里数两个量，缺一不可。**

1. **可见技能数**：会话落盘里技能清单（`skill-catalog` 的 `entries`）的条数。
2. **Skill 调用数**：同一会话里真实的技能加载调用条数（工具调用记录中 `name=skill`；工具定义里的同名字段不算）。

只看第 1 个数会得出「技能已经送达」；只有第 2 个数回答「技能有没有生效」。两个数一起看，才能把「通道修好了」与「机制起作用了」分开。

复算命令（dsh 会话以 zstd 压缩的 jsonl 落盘）：

```bash
zstd -dc <session.v3.jsonl.zstd> > /tmp/session.jsonl
# 可见技能数：会话里 skill-catalog 的 entries 条数
python3 -c "import json,re;d=open('/tmp/session.jsonl',encoding='utf-8',errors='replace').read();m=re.search(r'\"kind\":\"skill-catalog\".{0,4000}?\"entries\":\[(.*?)\]\}',d);print(len(json.loads('['+m.group(1)+']')))"
# Skill 调用数：真实工具调用记录里的 name=skill 条数
grep -o '"type":"tool-call","id":"[^"]*","name":"skill"' /tmp/session.jsonl | wc -l
```

**实测（项目技能交付通道修复前后，dsh 执行端会话）：**

| 样本（2026-09-11） | 可见技能数 | 其中 soia-dev | Skill 调用数 | 工具调用总数 |
|---|---|---|---|---|
| 修复前执行单 | 1（仅全局 `find-skills`） | 0 | 0 | 328 |
| 修复后执行单 A | 16 | 10 | 0 | 238 |
| 修复后执行单 B | 16 | 10 | 0 | 254 |
| 修复后执行单 C | 16 | 10 | 0 | 298 |

修复把可见技能从 1 项提到 16 项（含全部 10 个 soia-dev 技能，描述文本已是当时最新版），Skill 调用数没有跟着变：执行者看得到清单，一个技能正文都没进上下文。**通道送达不会自动带来技能生效。**

**边界（同批出现的反例）：** 同一批 16 项清单的会话里，也有加载了 2 次技能的执行单（工具调用 284 次）。所以这不是「必然为 0」，而是命中不稳定——对策是把「本单该加载哪几个技能」从「模型自己猜」变成任务书里的显式字段，而不是断言修好通道就等于修好行为。

**对策：** 派发方在任务书「适用技能」字段逐个列出本单技能名，执行者开工前加载全文，并在回报第一节写明实际加载项与未加载原因。字段格式与示例见 `soia-dev-agent-cli-dispatch/references/task-brief.md`；派发纪律见同技能 `references/dispatch-contract.md` 第 5 条；字段在输入契约里的必填位置见该技能 `SKILL.md` 的「输入契约」。

## 一手数据：触发词在真实任务书措辞下的命中情况（2026-09-12）

上一节的结论是「技能送达≠技能生效」；这一节回答**靠什么让它生效**，以及为什么触发词不是答案。

**三臂对照**（同一份零方法论指令的薄任务书，派给同基线的三个 worktree，唯一变量是任务书里有没有「适用技能」这一行）：

| 臂 | 技能可见 | 任务书写「适用技能」 | 实际加载技能数 |
|---|---|---|---|
| A | 是（14 个项目技能） | 否 | 0 |
| B | 否 | 否 | 0 |
| C | 是（14 个项目技能） | 是（只多这一行） | 6（3 个技能） |

同日全量核对：13 张「技能已送达」执行单里，带「适用技能」字段的 11 单全部加载，不带字段的 2 单全部 0 次。

**触发词为什么补不住。** 技能 frontmatter 的触发词是**动作措辞**，真实任务书写的是**问题措辞**，实测一个都不重叠：

| 技能声明的触发词 | 薄任务书实际写的 |
|---|---|
| 实现这个任务 / 修复这个 bug / 按任务书实现 / 修复缺陷 / 迁移 / 处理 findings | 把这份「哪些旧地址归到哪个 rail」的知识改成数据驱动：从一处集中的映射表读取，新增一条旧地址兼容不再需要改函数体 |

真实任务书描述的是**领域问题**，措辞空间随任务增长而无限，无法枚举；而 `soia-dev-agent-cli-dispatch` 所属仓的 `scripts/audit_skills.py` 对 frontmatter `description` 有 150 字符硬上限，逐条堆变体会挤占每次会话都要加载的技能清单预算。三臂对照也把变量钉死在字段上：A 与 C 只差「适用技能」这一行，加载数从 0 变成 6。**结论：触发词保留为兜底**（人类直接用口语发起、没有任务书的通道），主要机制是任务书显式字段——不要把「技能加载不上」的修复预算投在扩触发词变体上。

**边界：** 三臂对照的样本量是每臂 1 单、全量核对 13 单，够支撑「字段是有效机制、触发词不是」，不足以给出跨宿主、跨模型的加载率估计。表中「0 重叠」是该次对照里逐条比对得到的计数事实，不是对整体命中率的估计；本表不登记任何百分比形式的命中率。
