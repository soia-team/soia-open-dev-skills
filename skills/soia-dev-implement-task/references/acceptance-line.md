# 验收线：声明、裁决与完成契约

本文件是 `soia-dev-implement-task` 的验收线参考：**开工前声明验收线，收口时逐条对照证据裁决**。SKILL.md 的「验证并收口」按本文件展开。

规格侧的验收标准写法见 `soia-dev-draft-feature-spec` 的 `references/acceptance-authoring.md`；本文件管执行与裁决。

## 内容导航

- 完成契约：Closed 与 Open
- 开工前：验收线声明
- 负控：新检查必须能失败
- 判据自检：Clarity × Demand
- 收口裁决：逐条对照证据判定

## 完成契约：Closed 与 Open

收口只有两种形态，**没有「部分完成」这个中间态**：

| 契约 | 成立条件 | 交付内容 |
|---|---|---|
| **Closed** | 最强结论、适用授权、归属责任与实质风险都已解决；没有已知未知还能改变结论 | 全部验收项 `passed` 的判定表 + 变更与验证摘要 |
| **Open** | 上述任一项未解决 | ①当下可给出的**最强有界结果**；②**会改变决策的未知**；③该未知的 **owner 或归属缺口**；④**下一份证据或决策触发条件** |

Open 是结构化的开环交付，不是含糊的「还没做完」。写成 Open 时四段齐全，接手的人不必重新推导你走到哪。

低爆炸半径的内部选择可以只给一份简短比较与推荐就算完整：交付收在能改变结论的内容上；当兼容策略、迁移、恢复、守卫或治理产物不可能改变结论时，它们不属于本次交付。

## 开工前：验收线声明

在动手之前，把本次任务的验收线写成一行清单，每条都能被单独证伪：

```text
A1  <可观察结果>，证据：<命令 / 产物 / 复现步骤>
A2  <可观察结果>，证据：<...>
A3  <反例或边界>，证据：<...>
```

声明要点：

- **每条挂一个证据来源。** 声明时就写清拿什么证明它，避免收口时临时找证据。
- **逐条独立。** 一条失败不影响其余各条的判定，这样裁决表才有分辨力。
- **写得出的反例优先。** 能写出「什么情况下这条会失败」的条目才算可验证。
- **验收线先于执行。** 声明之后不再按实现结果回改验收项；确需调整时把它记成 Open 的一段，而不是静默放宽。

## 负控：新检查必须能失败

**每一条新增或改动的检查都要有一个可信的负控。** 一个从未失败过的检查与一个有效的检查在输出上同形；证明它有能力失败，才算证明它真的在检查。

四种可用的负控手法，任选其一并记下证据：

1. 观察修复前的失败（`fail → pass`）；
2. 临时回退或改坏被测行为，确认检查转红；
3. 植入一个范围受控的违规；
4. 使用一个已知违规的输入。

防线是可证伪性本身：守卫需要「已知或安全植入的违规能使它失败」的证据。检查无法失败时，把它标为未验证，并写明缺的是哪种负控。

## 判据自检：Clarity × Demand

验收线本身也要被审一遍。两条性质各自是杠杆：

- **Clarity（可判定）**：执行者能否分清「完成」与「未完成」。含糊的界（「理解到位」「基本可用」）会招来**过早收口**——注意力滑向「看起来做完了」。收紧界是第一顺位且成本最低的动作。
- **Demand（负载）**：它要求多少工作量。「每一个被改动的模型都已交代」比「产出一份变更清单」强制出更多调研；`Demand` 不绑定步骤，一条「全部规则已应用」同样给一份平铺的参考材料加上穷尽性门槛。

**最强的验收线同时是可判定的与穷尽的。** 自检时逐条问两句：这条能不能判出完成与未完成？这条能不能让偷懒的通过方式落空？

## 收口裁决：逐条对照证据判定

这是本技能自建的裁决步，三仓与本仓此前都没有这一步。收口时输出判定表，**逐条验收项对照它的证据给出三态之一**：

| # | 验收项 | 证据引用 | 判定 |
|---|---|---|---|
| A1 | <验收项原文> | <commit / 回执 / 命令与真实输出 / 产物路径 + 摘要> | `passed` / `failed` / `未验证` |
| A2 | ... | ... | ... |
| A3 | ... | ... | ... |

判定规则：

1. **三态，不设第四种。** 不用「基本通过」「应该没问题」「大概率」这类连续表述。含义模糊时判 `未验证` 并把缺的证据写出来。
2. **每条必须有证据引用。** 引用要能被人独立打开核对：完整 commit、真实命令与输出、产物路径加摘要。仅写「已测试」不是引用。
3. **`未验证` 必须带缺口说明。** 写清缺哪份证据、以及拿到它需要什么动作。
4. **`failed` 不因编号消失而消解。** 逐条给出 fix / reject / defer 与理由；不靠把条目合并、改写或删掉来制造通过。
5. **`passed` 只覆盖本条。** 一条通过不向上传染；整体结论由判定表本身承担，不由一句总结承担。
6. **执行者自报是待验证输入。** 判定表由主控独立复核后落定；外部 Agent 或下游脚本报的「完成」在复核前不构成完成。

判定表连同回执一起交付。全部 `passed` → Closed；存在 `failed` 或 `未验证` → 按 Open 的四段结构交付。

## 来源与承接说明

- **Closed / Open 双完成契约**：承接自 `lencx` 仓 `keel/SKILL.md` 的完成态定义（外部概念：Closed = 最强结论、适用授权、归属责任与实质风险均已解决，没有已知未知还能改变结论；Open = 最强有界结果 + 会改变决策的未知 + 其 owner 或归属缺口 + 下一份证据或决策触发条件）。本仓据此把「给出判断 + 下一步验证」升级为四段结构化开环交付。
- **负控要求（新检查必须能失败）**：承接自 `lencx` 仓 `coding-protocol/references/verification.md` 的 Prove Sensitivity 一节（外部概念：观察修复前失败 / 临时回退或改坏行为 / 植入范围受控的违规 / 已知违规输入，四选一）；keel 的守卫可证伪性表述与之同源，是跨仓重复出现的模式。
- **Clarity × Demand 双性质**：承接自 `mattpocock` 仓 `productivity/writing-for-agents/SKILL.md` 的 completion criterion 两性质（外部概念：Clarity 决定能否分清完成与未完成，含糊的界招致过早收口；Demand 决定要求多少调研负载；最强的判据同时是可判定的与穷尽的）。
- **本仓首创**：「**逐条 acceptance criterion 对照证据判定**」三步裁决步（验收项 → 证据引用 → `passed` / `failed` / `未验证` 三态）由本仓自建。三仓与本仓此前共同缺失这一步：`mattpocock` 的验收标准是编写时自声明，唯一核查它的是 `code-review` 的 Spec 轴，而该轴明确只报 findings 不做裁决；本仓现有验收要求（「验收证据先于执行」「完成边界」「只有实际执行记录才能改状态」）也未覆盖逐条判定。故此法不可承接，按本仓验收惯例自建。
- **实战素材（指令号）**：`owner-directives` 指令 222（v61 大对账把 `G0.0.4.28.17` 误写 passed，实况仅 M0/M1 并入且 M1 回执自述未通过——「图状态回写必须逐条附一手证据，对账批不得凭表述补 passed」）是判定表「每条必须有证据引用」与「`passed` 只覆盖本条」的一手来源；指令 193（15 个越界状态词改合法词，`check_goal_graph` 负向测试确认能红）是「三态、不设第四种」与负控要求的一手来源；指令 219③（每单验收时未解决问题逐条定去向后才销账）是 Open 四段结构「未知必须有 owner 与下一触发条件」的一手来源。
