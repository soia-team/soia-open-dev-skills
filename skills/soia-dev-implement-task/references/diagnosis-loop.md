# 诊断回路：先有一条能变红的回路

本文件是 `soia-dev-implement-task` 的缺陷定位参考：**在形成任何假设之前，先建立一条能在本次这个缺陷上变红的回路**。动手修一个缺陷、而复现路径尚不清楚时加载；SKILL.md「实施」第 3 条「缺陷先定位」按本文件展开，把「从输入、日志或失败测试复现」落到一条具名命令上。

回路是诊断里唯一困难的部分，二分、假设检验与插桩都只是消费它的机械动作。**先有回路，再有判断；没有回路，就没有下一步。**

## 核心门禁：先有一条能变红的回路

门禁只有一句：**在形成理论之前，先交出那条能变红的回路。**

判据是一条**具名命令**（脚本路径、测试调用、一行 curl），并且已经在本次诊断里**至少真实跑过一次**——把调用与输出贴出来，按下面的脱敏写法处理。它要在**本次这个缺陷**上会红、修好后会绿。

发现自己正在为「大概是什么原因」翻代码时，回到本门禁：理论再顺口也换不来一条会红的命令。这一步值得投入不成比例的精力，后面的一切才是机械工作。

## 十种回路造法

按偏好从高到低尝试；上一种走不通就换下一种，而不是缩小投入。

| # | 造法 | 适用与要点 |
|---|---|---|
| ① | 在能触达该缺陷的接缝上写失败测试 | 单元 / 集成 / e2e 皆可，接缝以真实调用点为先 |
| ② | 对运行中的开发服务跑 curl / HTTP 脚本 | 缺陷落在接口层时最快成形 |
| ③ | CLI 加 fixture 输入，与已知良好快照 diff | 输出可文本化时优先 |
| ④ | 无头浏览器脚本驱动 UI | 断言 DOM / console / network 中承载症状的那一个 |
| ⑤ | 回放抓取到的真实请求、payload 或事件日志 | 隔离跑过该代码路径，保留原始输入 |
| ⑥ | 一次性最小 harness | 系统的最小子集 + 一次函数调用 |
| ⑦ | 属性或 fuzz 循环 | 面向「有时输出错误」 |
| ⑧ | bisection harness | 做成可交给 `git bisect run` 的形状 |
| ⑨ | 差分回路 | 同一输入跑旧版本与新版本（或两套配置）并 diff 输出 |
| ⑩ | HITL bash 脚本兜底 | 必须有人点击时，用脚本驱动人，让回路仍有结构、输出可解析 |

**「有了一条回路」不是目标，「紧」才是。** 拿到回路之后，把它当一件产品继续打磨。

## 收紧三问

1. **能更快吗？** 缓存准备步骤、跳过无关初始化、缩小测试范围。30 秒的回路几乎等于没有回路，2 秒的确定性回路是诊断的放大器。
2. **信号能更锐利吗？** 断言具体的用户症状，而不是「没崩」。
3. **能更确定吗？** 固定时间、固定随机种子、隔离文件系统、冻结网络。

## 紧的四个性质：回路完成判据

四条同时成立，才可以进入假设阶段：

| 性质 | 判据 |
|---|---|
| **可变红** | 驱动真实缺陷路径并断言用户的**确切症状**；在本次缺陷上会红，修好后会绿 |
| **确定性** | 每次运行给出同样判定；非确定性缺陷用固定的高复现率替代 |
| **快** | 秒级，不是分钟级 |
| **可无人值守运行** | 执行者能自行跑完；人只通过 HITL 脚本这一种方式在环内 |

## 非确定性缺陷：抬高复现率

面向非确定性缺陷，目标不是干净复现，而是**更高的复现率**：循环触发、并行、加压、收窄时间窗、注入 sleep，直到比率高到可以对着它调试为止。**可调试的 50% 远好于不可调试的 1%**，把抬升比率当成回路本身的一部分来打磨。

## 无人值守与脱敏

**无人值守范式。** 回路默认以 unattended 方式运行：执行者离开后它仍能自行跑完。需要人参与时，只经 HITL 脚本这一种入口——脚本驱动人，人的回答以可解析输出回到执行者，而不是散落在对话里。

**脱敏写法。** 展示命令、输出与抓取产物之前先脱敏，秘密的位置写 `<REDACTED>`；回路针对环境变量构造，凭据留在环境里，不出现在展示内容中；抓取产物（HAR、日志、core dump）只引携带信号的行。脱敏后不足以诊断时，如实说明并再向用户要数据。

## 建不出回路时，以及收口动作

**建不出回路时**：停下并明确说明，列出已经试过的手段，向用户要（a）能复现的环境访问、（b）脱敏后的抓取产物、（c）临时插桩许可。拿到其中之一再继续；在回路不存在时进入假设阶段，正是本文件要挡住的那种失败。

**收口动作**（进入修复阶段时）：

- 修复前先写回归测试，但只在存在**正确接缝**时写：测试要跑在调用点真实发生的缺陷模式上。接缝太浅（单调用方测试对上多调用方缺陷、复现不了触发链的单元测试）只会给出假信心。
- 接缝不存在本身就是发现：登记为架构问题交下一轮处理，而不是用一个浅测试把缺陷锁成假象。
- 临时调试日志统一带 `[DEBUG-xxxx]` 前缀，结束时一次 grep 清空。
- 修复后重跑原始（未最小化）场景，确认它不再复现。
- 把被证实的假设写进提交信息，让下一个诊断者少走一次。
