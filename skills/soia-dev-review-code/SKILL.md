# soia-dev-review-code

## 客户可读说明

**能做什么：** 判断给定改动是否满足请求、是否引入具体风险；只读，不修复、不提交、不评论到远端、不合并。

**如何使用：** 提供 diff/PR/技能目录及目标。从现有材料确认候选版本或本地快照、范围和项目规则；可自行取得的 SHA/快照不向用户重复索要。无法取得必要材料时说明具体缺口，不猜版本，也不声称已审。

## 一次审查

1. **先看规格符合性。** 对照请求、已批准设计和验收行为读实际实现，不只看 diff 摘要；找漏做、做错或越界。已有架构是约束，不借审查另选一套。
2. **再看工程标准。** 沿直接调用边界检查正确性、输入安全、错误处理、兼容性和测试断言。只扩展与本次风险有关的视角，不按固定数量凑检查项。
3. **核实候选问题。** 回到原文和调用上下文，检查触发条件、反例与实际影响；能安全运行的聚焦检查可运行，外部副作用不作为审查手段。无法确认的疑点放到未验证项，不包装成缺陷。
4. **交付后停止。** 只报告会改变下一步动作的问题；按严重度给位置、触发条件、影响和依据。没有新 diff、新证据或显式要求，不循环复审。

默认一次审查。独立评审由一个符合用户/项目独立性政策的审核者执行，不等于双评估或 panel；同一实际模型换会话不能冒称异模型独立审查。仅在明确要求多视角/panel 时读取[多视角审查](references/independent-review.md)。同宿主用内置 subagent，外部 CLI 才使用 dispatch 技能。

## 什么算验过

上面四步判的是「改得对不对」。「验没验过」是另一件事，按下面取，不按记忆取：

1. **门清单以项目 CI 配置为权威。** 先取本次候选的改动路径（`git diff --name-only <基线>...HEAD` 加未跟踪文件），再从项目 CI 配置（例如 `.github/workflows/ci.yml`）逐条读出门，不从上一单的回执、也不从印象里抄。项目提供按改动路径解析 CI 配置、规则路由表与验证指南的影响面脚本时直接用它（例如输出「适用真源 / 必跑门 / 适用技能」三段的清单脚本）。这类脚本**只路由不判定**：它不执行门、不产生绿灯，它的退出码不是验收结论。
2. **按影响面的领域检查是补充，不是替代。** 项目验证指南按改动面点名的检查要逐条对表打开原文，命中的全跑；它补在 CI 门之外，不能用来缩减 CI 门。
3. **先量基线，再对拍增量。** 基线本身就有红项时，要证明的是「没让红变多」：同一环境下逐条给出本次 EC 与基线 EC，不把既有红算到本次头上，也不拿「基线本来就红」豁免新增的红。
4. **退出码要取对。** 用 `cmd >file 2>&1; echo $?` 取被测命令自身的退出码；`cmd | tail` 之后的 `$?` 是管道末尾命令的退出码，会把红报成绿。没实际运行的门写「未运行」，不用静态检查、历史证据或 `skipped` 冒充运行。
5. **跑门不破只读边界。** 只跑无副作用的检查；`--check` 类生成器不得改跑成 `--write`，不改工作树、不改产物、不改被审候选。需要缓存或数据根的检查用临时目录。

审查回执里把这几条的实际结果写清楚：跑了哪些门、各自 EC、与基线的对拍、哪些没跑及原因。门全绿也不等于建议通过，门有红更不等于本次改动有错——结论仍按上面四步的判断给。

## 被派发时的入口

已按用户或项目政策获准的一次独立评审使用以下入口；收到评审任务不再派发下一层评审。

- **输入**：候选标识（commit SHA / 快照摘要或内容指纹）、任务书或验收标准、本次改动范围、被审实现者所用模型标识（供 Independence Gate 当 `executor_model` 对照）。先从可访问材料固定候选；仍无法固定时说明缺口，不审一个会漂移的版本。缺实现者模型标识时独立性按 `blocked_independence` 处理，不写成「已独立复核」；这不妨碍对固定候选交付可证实的内容审查，但不能据此放行要求独立性的门禁。
- **输出**：声明实际审核者、模型证据和审查形态；一次合格独立评审不是降级。随后给建议、可核实问题和未验证项。只有原本要求 panel 而未完成时标明缺失侧，不把格式缺项当成代码缺陷。
- **不得改动代码**：全程只读，不修改、不提交、不评论到远端、不改工作树；需要生成缓存的检查用临时目录。审查前后核对候选未变，候选变了就把结论限定到已审版本。
- **结论不是放行**：这里交的是判断与问题清单，不是合并许可；放行由主控验收决定，本技能不因自动调用而获得修复权或提交权。

## 技能包分支

审技能时读取其正文和受影响资源：核对命令/接口、授权门、跨宿主可用性、元数据与依赖一致性。涉及行为变化，检查自检和实际输入的前向测试证据；目录存在或静态校验通过不等于有效。命令核实使用无副作用方式或官方文档，不运行发布、发送或安装来“验证”。

## 结果与边界

**日志与完成回执：** 先给建议，再列可行动问题与覆盖/未验证范围。无问题可以写“未发现可确认问题”，但不保证没有缺陷。可用“建议通过 / 建议先改 / 建议拒绝”；结论不是合并许可。

### 依赖与安装

无强依赖；使用目标项目已有工具，不自动安装依赖。安装与发布分别确认，默认项目、明确宿主、单技能。
项目安装：`npx skills add soia-team/soia-open-dev-skills -a <agent> -s soia-dev-review-code`；执行前核实当前 CLI 参数。
整域需明确选择：先接入市场 `soia-team/soia-open-skills`，Claude Code 用 `claude plugin marketplace add` / `claude plugin install soia-dev@soia`，Codex 用 `codex plugin marketplace add` / `codex plugin add soia-dev@soia`；完整步骤见[官方安装说明](https://github.com/soia-team/soia-open-skills#安装)。
WorkBuddy 使用[专家安装说明](https://github.com/soia-team/soia-open-skills/blob/main/docs/install/workbuddy.md)，不由 npx 代装；上述命令不构成安装授权。

**私密信息与中间数据：** 只读约定范围；不展示秘密或无关源码。检查可能生成缓存时使用临时目录；不改源码、规范、测试或工作树状态。审查前后核对候选未变，变化时把结论限定到已审版本。
