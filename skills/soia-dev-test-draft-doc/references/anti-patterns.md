# 测试设计反模式

本文件是 `soia-dev-test-draft-doc` 的测试设计参考：**评审用例草稿时认出三种会让套件失去分辨力的反模式，并给出正向改写目标**。SKILL.md「测试设计」第 3 条（每例给出可执行前提、步骤和明确预期，高风险行为需有对应负向证据路径）按本文件展开。

本技能只设计测试、不执行测试，也不接管 TDD 实现；本文件因此定位在**用例草稿与评审判据**，不写成循环操作手册。写用例时逐条对照三种反模式，交付前用文末自检收口。

## 内容导航

- 三种反模式：实现耦合 / 同义反复 / 横向切片
- mock 边界：只出现在系统边界
- 命名读作能力
- 与起草侧负控要求挂钩
- 交付前自检

## 三种反模式总览

| 反模式 | 一句话识别 | 正向目标 |
|---|---|---|
| 实现耦合 | 行为没变，改一个内部名字测试就红 | 在公开边界上观察行为 |
| 同义反复 | 期望值按被测代码同样的算法算出来 | 期望值来自外部真源 |
| 横向切片 | 一批测试先落地，实现还没写 | 纵向切片，先打通一条端到端路径 |

三种反模式可以同时出现在一条用例上：一条批量先写、又 mock 内部协作者、期望值还由被测代码现算的用例，三行都命中。逐条判定时按行分开改写，一次只修一种。

## 实现耦合（Implementation-coupled）

| 维度 | 内容 |
|---|---|
| 识别特征 | 改一个内部函数名、拆一个私有方法，行为没变而测试转红；用例里 mock 本仓自己的协作者、断言调用次数、用数据库查询代替接口返回做验证 |
| 反例 | 「结算调用 `paymentService.process` 一次」——它断言的是这次调用发生过；内部改走另一条路径就红，而用户看到的结算结果没有变化 |
| 正向目标 | 在公开边界上观察行为：给定有效购物车，结算返回订单号且该订单出现在用户的订单列表；重命名或重排内部实现不破坏套件 |

## 同义反复（Tautological）

| 维度 | 内容 |
|---|---|
| 识别特征 | 期望值与被测代码共享同一段计算逻辑或同一个常量，测试构造上必过；出现「把期望值再算一遍」的表达式、按实现逐字生成的快照、与自身相等的常量断言；把实现改坏时用例仍然通过 |
| 反例 | `expect(total(items)).toBe(sumBy(items, priceOf))`——期望值用与实现相同的口径现算，永远不会与实现分歧 |
| 正向目标 | 期望值取自外部真源：已知良好字面量、手算过的例子、规格或需求原文。「3 件单价 12.5、满 30 减 5，应收 32.5」这类期望值，第二个人能独立复算出来 |

## 横向切片（Horizontal slicing）

| 维度 | 内容 |
|---|---|
| 识别特征 | 先落一批测试再写实现；批量用例验证的是想象行为，检查的是对象的形状（字段齐不齐、方法在不在）而不是用户实际做的事；实现还没理解，测试结构已被锁定 |
| 反例 | 一次提交 20 条用例覆盖「全部 service 的返回结构」，多数在实现落地前就写死内部结构；实现换了形状后集体返工，返工量集中在测试而不是行为 |
| 正向目标 | 纵向切片：先 tracer bullet 打通一条端到端路径（一条用例 → 最小实现 → 观察结果），再逐条扩展；每条新用例回应上一轮学到的东西 |

## mock 边界：只出现在系统边界

| 边界 | 可以 mock 什么 | 为什么 |
|---|---|---|
| 外部 API / 第三方服务 | 支付、短信、物流等外部调用 | 真实调用不可重复、有成本或带副作用 |
| 时间 | 当前时刻、时区、超时计时 | 结果依赖运行时刻，用例无法复现 |
| 随机 | 随机数、ID 生成、采样 | 同一输入要得到同一条期望值 |
| 文件系统 / 数据库（必要时） | 仅在跨进程且拿不到真实实例时 | 边界外的持久化状态，用接口观察比查库更稳 |

三条口径：

1. mock 只出现在系统边界；本仓自己的模块之间直接调用，模块内部协作者用真实实现。
2. 每条边界在用例里写清 mock 的是哪个外部依赖、以及为什么必须 mock；写不出理由的 mock 先删掉再评估。
3. 「测试需要隔离」与「测试要观察真实接口行为」冲突时取后者：把隔离点放在系统边界，而不是在被测模块内部加缝。

## 命名读作能力

| 差（读作内部实现） | 好（读作能力） |
|---|---|
| 「结算调用 `paymentService.process`」 | 「用户可以用有效购物车结算」 |
| 「`OrderMapper` 返回 `OrderDTO`」 | 「已支付订单出现在用户的订单列表」 |
| 「`retry()` 被调用 3 次」 | 「外部接口超时后订单自动重试并最终成功」 |

自检读法：把用例名念给不熟悉该模块的人听，他能说出「现在有什么能力可用」；若只能说出「哪个函数被调了」，说明用例还贴着实现。

## 与起草侧负控要求挂钩

- **期望值可追溯。** 每条用例的期望值要能追溯到外部真源：已知良好字面量、手算例子、规格或需求原文；追溯不到时先补真源，再写断言。
- **每条配反例或负控说明。** 写清「什么情况下这条会失败」。负控口径见 `soia-dev-draft-feature-spec/references/acceptance-authoring.md` 的负控一节；高风险路径上的用例另给负向证据路径。
- **负控随用例同批交付。** 本技能不执行测试，但要让执行者拿到用例就能验证；负控说明是下游「新检查必须能失败」的前置输入。

## 交付前自检

1. 每条用例都能指出它观察的公开边界，重命名内部实现不影响判定。
2. 每条期望值都能指回外部真源，且能被第二个人独立复算。
3. 每条用例配了反例或负控说明，高风险路径另给负向证据路径。
4. 用例按纵向切片组织，tracer bullet 排在最前，同一批里没有「先落一批测试再补实现」的结构。
5. mock 只出现在系统边界，每条都注明了被 mock 的外部依赖与理由。
6. 用例名读作能力，不读作内部调用。

## 来源与承接说明

- **三种反模式及其 tell**：承接自 `mattpocock` 仓 `docs/engineering/tdd.md`（外部概念：implementation-coupled / tautological / horizontal slicing 三条反模式及各自的 tell——改内部函数名而行为未变就红、期望值按代码同样方式算出因而构造上必过、一批测试先于任何实现落地；另有 mocks are for system boundaries only；vertical slice 以 tracer bullet 打通一条端到端路径，横向切片验证的是想象行为、检查形状而非用户实际做的事，并在理解实现前锁定测试结构）与 `skills/engineering/tdd/SKILL.md` 的 Anti-patterns、What a good test is 两节（外部概念：测试通过公开接口验证行为、读起来像规格并能存活于重构；期望值必须来自独立真源——已知良好字面量、worked example、spec；测试名读作能力而非内部实现）。本仓改写为中文用例评审判据，并按本技能边界压缩。
